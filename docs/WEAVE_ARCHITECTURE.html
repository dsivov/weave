Weave — architecture

Three deployables over one governed graph. A library core that knows nothing about HTTP, a product layer that owns the team model, and surfaces — REST, MCP, SSE, CLI, the web UI — that are all adapters over the same handlers. Every port has exactly the adapters the three supported deployments need, and no more.

Guiding principle

Every surface is an adapter over one governed core

An adapter that holds state has become a second source of truth — and every failure this system is designed to prevent starts there.

The rules that follow all derive from it. The core is a library and knows nothing about HTTP, so it cannot grow a private request-scoped cache. A question has one handler, and REST and MCP are two thin adapters over it, so the human and agent answers cannot drift (A9, A10). Configuration is the signed ledger version the runtime reads, so a wizard cannot become a config the runtime ignores (A8). An artifact node carries a locator rather than a copied body, so the index cannot disagree with the repository (A5). And the fleet reconciles to state it reads back rather than to commands pushed at it, so a supervisor's intent lives in one place (A15).

Key flows

A governed write, end to end — and how it reaches every watcher

The fleet flow inverts the arrows and is the reason the system works across networks it does not control: the dev-host daemon opens the connection, never the server. It registers, then heartbeats; the reply carries the control state and desired_workers; the daemon reconciles its containers to match. A supervisor scaling a machine writes a number onto the host record — the machine learns it on its next beat. Nothing is ever pushed to a host, which is what lets one sit behind NAT (A15).

◆ Replacing an incumbent
Four replacements, each with a phase that deletes the old one — they never coexist past a milestone. python-jose → PyJWT (P0). AUTH_ACCOUNTS/AUTH_ROLES → the user store (P1). 4-second polling → SSE (P3). Task reviews/learnings list fields → Review/Insight nodes (after M2 sign-off).
Boundaries & ownership

Who owns what

◆ The boundary in one line
weave_core owns the graph and the verdicts and knows nothing about who is asking; weave owns the team, the identities and every byte of HTTP; weave-ui owns only rendering. They meet at service functions — never at a shared mutable object, a global, or a request-scoped cache.
Trade-offs

What we chose against

One decision deserves the space, because the RFC left it implied and the failure it prevents is silent. The event bus is single-process by construction — the source's own docstring says so: "Single-process async pub/sub… not durable… swap to a broker later." Meanwhile the server supports gunicorn with --workers N. Put SSE on that bus unchanged and a client connected to worker 2 will never see an event published on worker 1. Nothing errors. The board just quietly stops updating for some users.

DecisionChosenRejectedWhy
Event fan-out across workersTwo adapters behind the existing port: in-process for single-process deployments, PostgreSQL LISTEN/NOTIFY for multi-workerRedis pub/sub · a real broker (NATS, RabbitMQ) · pinning every deployment to one workerA broker is a new dependency and a fourth service to run, both barred without a decision (A11, A1). asyncpg is already installed and already required for the multi-user path, so the fan-out costs nothing new. One worker forever would cap the product at a scale we intend to exceed.
Persistence shapeThe existing RecordStore port with memory/json/postgres adaptersSQLAlchemy or another ORMAn ORM is a new library for a job a working, tested abstraction already does — and it would only cover the Postgres path, leaving the file path on a second mechanism.
MCP surfaceTools are adapters over the same service functions the routers callIndependent tool implementations, as in the sourceTwo implementations of one question drift, and the drift is invisible until a human and an agent disagree in a review (A9).
Web UI deliveryBuilt into the server image, served as static assetsA separately deployed front end behind its own server or CDNA fourth deployable to run, version-match and onboard, against a measured onboarding target. It also buys nothing: the UI has no traffic profile the API server cannot serve.
Document referenceLocator (repo · path · rev) resolved through a registered layoutStoring artifact bodies in the graphA copied body rots against the repository, and reconciling the two becomes a permanent background job. A locator that stops resolving is a detectable defect instead (A5).
Graph backendNeo4j as the optional dedicated engineMemgraphSame driver shape and a similar feature surface, but wider operational familiarity — and only one of them can be gated at every milestone (A4).
Shared edit convergenceVersion-checked writes: 409 plus a merge view, on the ledger that already versions everythingCRDT co-editing (pycrdt + Yjs)Two libraries across two runtimes, ahead of demonstrated need, for artifacts that are mostly edited by one person at a time. Deferred behind the transport seam, revisited if the merge-conflict rate justifies it.
Human clientOrdinary Claude Code — CLI, app, IDE extensionA bespoke desktop or terminal clientA second client architecture to build and keep in step with the agents' surface, replacing one that already works remotely over Streamable HTTP (A10).
