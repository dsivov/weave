The team is the product

Weave has been a flagged subsystem inside a knowledge-graph server — real, working, and installable only by hand. It becomes the product: a multi-user, multi-role workspace where humans and autonomous agents plan, build and review on one governed graph, and where standing that up is a wizard rather than a 599-line env file.

The problem

A working dev team you can only install by hand

Weave already does the hard thing. Three governed roles — Manager, Architect, Developer — plus an Integrator, coordinating through one graph instead of through files on one machine. Tasks are claimed atomically, decisions are recorded as typed edges, and an autonomous developer container drains a queue and opens PRs while a human sleeps. That part works.

What does not work is everything around it. Weave lives as context_graph/weave/ — roughly 4,270 lines on the feat/weave-p0 branch, 23 commits ahead of main, ten phases of work (P0 → P9) that are not merged, gated behind ENABLE_WEAVE. To run a team, you first install a knowledge-graph server and configure it: a 599-line env.example carrying 53 settings, a config.ini, and six preset JSON files (468 lines: ontology, actions, RBAC, lifecycle, rules, seed) that ship inside a Python package.

The WebUI is not the gap here — it already has real editors. An Ontology manager and a Rules manager. A Studio that versions and signs every change through a propose → diff → sign gesture. A conversational Get Started that interviews the project lead and proposes a config for approval before installing anything. That machinery is good, and it is generic: it speaks the graph's vocabulary — object types, edge types, rule predicates, action catalogs — so configuring a team means translating your decisions about review policy, hand-offs and autonomy into graph primitives yourself, from a blank object type rather than from something that already looks like a dev team. And the two things that most define how a team works — RBAC and the lifecycle state machines — have no editor at all: Studio versions rule, ontology, flow and action, not those. For them the preset files on the server are still the only interface.

onboarding

53 documents

Context Graph's docs/ holds 53 files. Most explain the graph engine — quadruples, ontologies, ingestion. Almost none of it is what a new team member needs in order to do their job on day one.

multi-user

One operator at a console

Workspaces isolate projects and RBAC is real, but the surface above the graph assumes a single operator. Two people on the same board cannot see each other, cannot see a doc being edited, and have no story for editing it together.

control

Autonomy with no seat beside it

The developer role is autonomous or it is nothing. A human lead who wants to steer a fleet — claim an epic, fan it out, redirect a worker — is described as optional and has no first-class place in the control path.

The single-machine assumptions surface the moment a real fleet runs. In the milestone review of 2026-08-04 the atomic task claim turned out to be locked per task rather than per workspace: two workers claiming two different tasks took two different locks, so both could enter code that touched the same module — the exact collision the design promised to prevent. It was caught by review and fixed in 98e76b22 before anyone shipped on it. That is the process working. It is also the tell: a system built as a feature of a single-user product carries single-user assumptions into every corner until you go looking for them.

The idea

Invert the stack — the engine goes underneath

A governed graph makes a superb engine and a poor front door.

Nothing about Weave needs to be rewritten. It needs to be turned the other way up. Context Graph stops being the product that Weave is a feature of, and becomes the engine that Weave runs on: ontology, RBAC, lifecycle guards, rules, events — the machinery that makes a hand-off auditable. Weave becomes the thing a team actually opens in the morning: a workspace with a live board, seats for people and agents, and wizards that author configuration instead of asking you to hand-edit it.

That inversion is not cosmetic. It decides what the repository is, what a release means, who the documentation is written for, and — most of all — what has to be true before a second person can log in. Context Graph stays what it is: a generic, decision-aware graph product in its own directory, with its own life. Weave gets its own repository, its own layout, and the freedom to make choices a graph product would never make.

How it works

Three changes carry most of the weight

The first is that configuration becomes Weave-shaped. The machinery is already there and it works: Studio signs and versions every artifact through propose → diff → sign, and the Get Started interview already turns a conversation into a proposal a human approves before it installs. What is missing is a layer that speaks the team's language instead of the graph's — a wizard that asks who signs off on a schema change and how many developer containers run, starts from Weave-oriented templates rather than a blank object type, and writes the ontology, rules, actions, RBAC and lifecycle that follow. Two of those five bypass the signed ledger today; Weave brings them in, so the whole configuration is one versioned object and what you edit is what the runtime enforces.

The second is that the team becomes plural in the surface, not only in the data model. Weave is multi-user from the first screen: presence on the board, live task and document state, and collaborative editing of the artefacts a team actually fights over — PRDs, RFCs, diagrams, the ontology itself. Agents already coordinate through the graph; people should get the same guarantee, which means concurrent edits that converge rather than a last-write-wins save button.

And the seat that is missing today gets built. A senior developer is a supervisory principal, not an escape hatch: they read the governed plan, claim and order work, dispatch autonomous workers, and pause or redirect one that has gone sideways — through the same claim protocol every agent uses. Autonomy is preserved because supervision does not bypass the lifecycle; it operates it.

Read the three figures together and the shape of the product falls out. A team opens Weave, runs a wizard to describe how they work, sees each other on a live board, and watches a mixed fleet of people and agents pull from one governed queue — with a human who can lead it rather than only switch it on and off.

Why now

The invention risk is already behind us

This would be a reckless thing to start if the mechanism were unproven. It is not. Ten phases landed on the branch, ending with the dev host and the developer container — the pieces that make a distributed fleet real rather than notional — and a testbed project exists specifically so the autonomous developer builds something real on a branch per task.

The authoring machinery landed too, and on main rather than a branch: the Studio ledger that signs and versions every artifact, the ontology and rules editors, and the Get Started interview that proposes a config for human approval before it installs. (The visual diagram editor and the Weave board are still branch-side.) So the wizard this post argues for is not a new mechanism — it is a Weave-shaped layer on a proven one, plus two artifact kinds the ledger does not yet cover.

The design premise that made it possible also held up. There is no orchestrator model: every reasoning step is a first-party Claude Code session, and every coordination step is deterministic graph logic — governed actions, lifecycle guards, events — that needs no model at all. That removed the dilemma an earlier attempt died on, and it is what lets a fleet scale without a model sitting in the routing path metering every hand-off.

And the method has teeth. The fleet race in the claim lock was found by a milestone review and closed before it could burn anyone, which is the entire argument for doing this work docs-first. What remains is not invention: it is a repository of its own, a rebrand, wizards, presence, collaborative editing, a supervisory seat, and the unglamorous productisation — tests, deployment, and documentation aimed at a person doing a job rather than at a graph engine.

▲ Stated honestly
Weave is not shipped. It sits on feat/weave-p0, unmerged, off by default, and installable only by someone who already knows Context Graph. Every capability in this post that is described in the future tense is future tense on purpose.
Where this goes

From a flag to a front door

The RFC proposes the phased path: give Weave its own repository by copying the engine across and renaming it wholly — a standalone server with no dependency on the parent, which stays a generic product, untouched; add a team-vocabulary wizard beside the existing graph-vocabulary editors and bring RBAC and lifecycle into the signed ledger; make the surface genuinely multi-user with presence and converging concurrent edits; build the senior-developer seat as a governed supervisory principal; and finish with productisation — packaging, deployment, tests, and documentation written for the job rather than the engine.

One target should be measured rather than asserted, because it is the whole point: onboarding a new team member onto Weave must be demonstrably faster than onboarding them onto Context Graph today. Time it, publish the number, and let it govern what the wizards must cover.
