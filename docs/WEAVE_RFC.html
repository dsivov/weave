Weave — RFC & build plan

Stand Weave up as a standalone product: copy the engine and governance layers out of the parent tree into a new repository, rebrand them completely, and build the six things the parent never had — a real user store with an admin UI; a data model that answers the team's four standing questions and links every entry back to the real document; a live multi-user surface; team-vocabulary setup wizards; a supervisory seat beside the autonomous fleet; and a one-command onboarding bundle that brings up the server, the database and the container dev agents. Seven phases, seven milestones, and no new external library.

Motivated by BLOG_THE_TEAM_IS_THE_PRODUCT.html · source inventory taken from the parent tree at feat/weave-p0 (head 608401b8, 23 commits ahead of main)
Summary

Fork the engine once, brand it wholly ours, and build the product the parent could not

What we assemble

The proven layers, copied and renamed: the governed graph and CGR3 decision retrieval; rbac · lifecycle · actions · rules · ontology; the Studio signed ledger and diagrams; the event bus; document ingestion; the whole Weave team layer (coordinator, atomic claim, fleet registry, integration gate) and the dev-host bundle (registry + daemon, 1,072 LOC — outbound-only heartbeat, reconcile, drain, one seat per machine); the React WebUI and its 28 components. ~92k LOC across Python and TypeScript.

What we build

A persisted user store + Admin ▸ Users UI — the parent has none. The answer surface: Feature, Review, Insight, Question as real nodes, plus a locator on every artifact so the index leads back to the document in the project layout. A live transport (SSE on the existing bus) with presence, replacing 4-second polling. Team-vocabulary wizards over the signed ledger, plus RBAC and lifecycle as ledger artifact kinds. The senior-developer seat. And a one-command onboarding bundle — a weave CLI and compose stacks for the server, the database, and the dev-host daemon that proxies a developer environment to Weave and carries the container fleet.

What we avoid

Any edit to Context_Graph/. Any runtime dependency on it — no submodule, no upstream package, no shared venv. Six storage backends we will not test. The web scraper, the evaluation harness, and lightrag.tools. CRDT co-editing in v1 (named seam, deferred). Federation of per-developer graphs. Any surviving use of the names Context Graph or LightRAG.

Decisions

The choices this plan is built on

D-002
Standalone by copy, not by dependency — the selected modules are copied into a new repository and renamed. Because Weave must be a product with its own release, brand and roadmap, and an upstream dependency would drag the parent's naming, config surface and release cadence with it. (Rejected: git submodule — keeps the forbidden names in every path; upstream pip package — same, plus couples releases; monorepo — violates "standalone".)
D-003
Zero writes to Context_Graph/ — one-way, verified. The parent tree's git HEAD and working-tree checksum are asserted unchanged in CI. Because an intention is not a control. (Rejected: "we'll be careful".)
D-004
Total rebrand, enforced by a name-guard — no occurrence of lightrag or context graph in any filename, module path, environment variable, database identifier, UI string or document. Because a half-rebrand is worse than none: it teaches everyone the old names anyway. (Rejected: rebrand the UI only; rebrand incrementally per phase.)
D-005
Two Python packages — weave_core/ (engine) and weave/ (product), plus weave-ui/. Because the engine has a plausible independent life and the split keeps the team layer from reaching into graph internals. (Rejected: one flat package — no seam; a third brand for the engine — a second name to explain in every doc.)
D-006
conda as the dependency manager, environment.yml as the manifest. Because it is the house default and handles the non-Python pieces (database clients, native wheels) directly. Asked, not assumed (R9). (Rejected: uv — better source alignment, since the parent ships uv.lock, but not the house default; poetry; pip + venv.)
D-007
Three storage paths: file-based, PostgreSQL, Neo4j — 9,406 of 18,740 LOC of backend code. Because file-based makes first-run trivial, Postgres covers KV + vector + graph in one production service, and Neo4j gives teams that want a real graph engine one. (Rejected: Mongo, Milvus, Memgraph, Redis, Qdrant, Faiss — 7,617 LOC nobody would gate per milestone.)
D-008
Keep ingestion and retrieval, drop the scraper — the brain needs document extraction and CGR3 precedent for orient and curated backfill. Because those are load-bearing for the team story; web crawling is a parent use case. (Rejected: keep webingest 1,819 LOC + lxml + playwright; drop RAG entirely — kills semantic precedent.)
D-009
A real user store replaces AUTH_ACCOUNTS — persisted users with bcrypt hashes, governance roles and per-workspace membership, managed in an Admin UI. Because the parent has no user store at all: auth.py parses 'admin:admin123,user1:pass456' from an environment variable once at boot, with zero CRUD routes and no table anywhere, so adding a person means editing .env and restarting. It reuses the Weave RecordStore pattern (in-memory + JSON + Postgres) and the bcrypt and PyJWT already present. (Rejected: extend the env string; adopt an external IdP in v1.)
D-010
Live updates over SSE on the existing event bus; optimistic concurrency for shared edits. Because the transport is server→client, an in-process bus with a durable ingress log already exists with nothing attached to it, and Starlette streams responses without a new library — while the Studio ledger already versions every artifact, so a version-checked write yields a 409 and a merge view instead of a silent overwrite. (Rejected: WebSocket — bidirectional capability we do not need, and a uvicorn extra; CRDT co-editing — deferred behind a named seam, revisited if artifact merge conflicts become common.)
D-011
The data model gains four answer-bearing node types — Feature, Review, Insight, Question. Because Weave has to answer four question classes for humans and agents alike — what changed · why · what does it do · what did we learn — and today only the first two have nodes. Functionality has none at all, and reviews and learnings are persisted as plain fields inside a task record (store.py:41-44), so they cannot be queried, linked or cited across the graph — while the declared reviewed_in link type has no node to point at. (Rejected: keep them as task fields and answer by full-text retrieval — unciteable and invisible to traversal.)
D-012
Every artifact node carries a resolvable locator — repo · path · rev · anchor, plus a registered ProjectLayout that turns those into a link a human can open and a file an agent can read. Because the graph is an index, and an index whose entries do not lead back to the document is trivia: of 14 node types only Module.path, PullRequest.url and Environment.url carry a locator today — PRD, RFC, ADR, Diagram, ChangeRequest and Task carry none, and Commit has only a subject line, not a sha. (Rejected: store document bodies in the graph — duplicates the repo and rots; convention-based paths — breaks the moment a team reorganises.)
D-013
Onboarding is a product surface, not a library — a weave CLI, a compose bundle, and role-install scripts. Because the pieces exist but nothing assembles them: scripts/ is empty, the compose file has a single service pulling the parent's upstream image with no Weave in it, all four console entry points are lightrag-*, and there is no weave command at all — so standing up a team means calling Python functions by hand. (Rejected: document the manual steps better — the measured onboarding target cannot be met by prose.)
D-015
Every role is a Claude Code session, and the two LLM paths never merge — humans run it interactively (CLI first, plus desktop app and IDE extension), dev agents run it headless in a container, and both speak the same MCP surface over HTTP so a role works unchanged on a remote machine. Every such seat is subscription only: anthropic is not a dependency, and no API key, auth token or base-URL override reaches a Claude Code process. Server-side LLM use — graph build, extraction, embedding, retrieval, rules — runs through the configurable backend connectors and is the only place a model credential exists. Because subscription-based access is a hard limitation of this architecture, and one client architecture cannot drift from itself the way two would. The parent already enforces this for containers (preflight_subscription_auth() scrubs ANTHROPIC_API_KEY and friends); this extends the same boundary to human seats. (Rejected: a bespoke human client; any SDK-based agent runtime.)

These are logged in DECISIONS.md as D-002 … D-015 and not re-opened without a new decision entry.

Data model

One index the whole team asks — and every entry leads back to the real document

Weave is the team's primary source of truth. A person joining on Tuesday and an agent claiming a task at 3am ask the same four questions, and both should get the same answer from the same place: what changed · why · what does it do · what did we learn. The inherited model answers the first two well and the last two not at all.

What the inherited model has, and what is missing

Question a team member asksNode types todayLocator todayChange proposed
What changed, and where did it land?ChangeRequest · Task · Commit · PullRequest · IntegrationRunPullRequest.url only — Commit has no shaadd sha + locator
Why was it done this way?ArchitectureDecisionRecord + RelationContext (decision_trace, approved_by, policy_ref, valid_from/until)noneadd locator so the ADR resolves to the real file
What does this system actually do?no node type — Module is code-structural; PRD/RFC are documents—new Feature + implemented_by / specified_by / depicted_by
Who reviewed it, and what did we learn?no node types — reviews / learnings are list fields on the task record; reviewed_in points at nothing—new Review + Insight, promoted to first-class nodes with a one-time migration out of the task fields
Has anyone asked this before?no node type — retrieval only, nothing citable—new Question — an asked-and-answered node linked to whatever answered it
Where is the full document?—3 of 14 types: Module.path, PullRequest.url, Environment.urllocator on every artifact node + ProjectLayout registration
◆ Why a locator and not the document itself
The graph stays an index over the team's repositories, never a second copy of them. A node carries repo · path · rev · anchor; the registered ProjectLayout turns that into a URL for a person and a readable file for an agent. Nothing has to be kept in sync, because nothing is duplicated — and a node whose locator no longer resolves is a detectable defect rather than silent rot.

Roadmap

Seven phases, one critical path

Phases

Deliverables, and the gate each must pass

P0 · Fork & rebrand → M0 mechanical
ships: the selected ~92k LOC copied into weave_core/, weave/, weave-ui/; every module path, env var, storage identifier, UI string and document renamed; the copied test suites; the CI name-guard; PROVENANCE.md pinning the source commit. No behaviour change of any kind.
gate: (1) the copied test suite passes at the same count as in the source; (2) grep -ril 'lightrag\|context.graph' over the whole repo excluding .git returns 0 hits — including filenames; (3) the parent tree's git status is clean and its working-tree checksum matches the pre-phase value byte for byte; (4) the server boots and serves the UI against file-based storage.
P1 · Standalone server & the user store → M1 the gap you hit
ships: WEAVE_* configuration surface; a persisted user store on all three storage paths (bcrypt hashes, governance role, per-workspace membership, active/disabled); user CRUD routes; Admin ▸ Users in the UI; one-time migration of any AUTH_ACCOUNTS/AUTH_ROLES value on first boot, then removal of both from the config surface; Postgres and Neo4j deployment paths.
gate: (1) an admin creates a user in the UI, that user signs in, and sees only the workspaces granted — asserted, not eyeballed; (2) a user holding developer receives 403 on an architect-only governed action; (3) an install configured the old way migrates its accounts on boot and then serves with AUTH_ACCOUNTS unset; (4) grep -r AUTH_ACCOUNTS returns 0 outside the migration path; (5) the same suite passes green on file-based and Postgres and Neo4j.
P2 · The data model & the answer surface → M2 the team's source of truth
ships: Feature, Review, Insight and Question as first-class node types with their link types; a one-time migration lifting existing reviews and learnings out of task records into nodes; a locator (repo · path · rev · anchor) on every artifact node and sha on Commit; the ProjectLayout registry; and the four canonical queries exposed to both the UI and the agent tool surface.
gate: (1) each of the four questions — what changed · why · what does it do · what did we learn — is answered by a single traversal returning nodes, not a text blob; (2) every artifact node returned by those queries resolves through its locator to a file that exists at the named revision — a dangling locator fails the gate; (3) an agent asks via MCP and a human asks via the UI and receive the same node set for the same question; (4) the migration moves 100% of existing task reviews/learnings with no loss, asserted by count and content; (5) reviewed_in now terminates on a Review node — no declared link type points at nothing.
P3 · Live, multi-user surface → M3
ships: an SSE stream fed by the existing event bus; presence (who is on this board, who is editing this artifact); the board, task states and fleet status updating live; version-checked writes on Studio artifacts returning 409 plus a merge view; all polling removed.
gate: (1) two authenticated sessions — a task claimed in one appears in the other in under 1 second with no reload; (2) two sessions editing one artifact: the second write is rejected with 409 and the merge view is offered — a silent overwrite fails the gate; (3) grep -r setInterval in the board code returns 0; (4) a concurrent-writer test drives N simultaneous claims and asserts exactly one winner on each storage path — the JSON store included.
P4 · Team-vocabulary wizards → M4 the main goal
ships: a setup wizard that asks in team language (who signs off on schema changes, how many developer containers, which task states you use) and writes ontology, rules, actions, RBAC and lifecycle through the signed ledger; Weave-oriented starting templates; rbac and lifecycle added as ledger artifact kinds so they are versioned and signed like the rest.
gate: (1) from a fresh install, a wizard run produces a governed workspace with roles and gates enforced — with zero file edits and zero restarts; (2) an RBAC change made in the wizard is enforced on the next request, observed as a 403 that was a 200 before; (3) a lifecycle change is observed as a 409; (4) both appear in ledger history with an attributed signature and a diff; (5) rolling back to the prior ledger version restores the prior behaviour.
P5 · The senior-developer seat → M5
ships: a supervisory principal that claims and orders work, dispatches autonomous workers, and pauses / resumes / stops / redirects them; a review queue; every supervisory act recorded as an attributed decision.
gate: (1) a senior developer dispatches N workers and each appears in the fleet registry with a live heartbeat; (2) a pause is honoured between steps — the worker's last action completes and no edit is left half-written; (3) every supervisory action is present on the graph with an authenticated principal, none self-stamped; (4) the pre-existing claim tests still pass unmodified — supervision must not have changed the claim protocol.
P6 · Onboarding bundle & productisation → M6 the measured goal
ships: a weave CLI as the single entry point — weave init (workspace + preset), weave roles install, weave user add, weave project register (the ProjectLayout), weave up (the bundle), weave agents up / scale / down; a compose bundle carrying the Weave server, Postgres (optional Neo4j), and the dev-host daemon that manages the container-based dev agents; the rebranded dev-agent image; role-kit generation wired to the CLI rather than called as a Python function; the conda environment; documentation written for the job rather than the engine; and the onboarding measurement itself.
gate: (1) on a clean machine with only Docker and the repo, the published steps reach a running Weave with an admin user, installed roles, a registered project and N dev agents visible in the fleet — no Python called by hand, no tribal knowledge; (2) weave agents scale 3 results in exactly 3 registered workers with live heartbeats, and down retires them cleanly; (3) scripts/ and [project.scripts] contain a Weave path for every step the docs mention — a documented step with no command behind it fails the gate; (4) onboarding time is measured and published, and is lower than the parent's baseline measured the same way — the target the blog set; (5) no document in docs/ references the parent's product names.

Full task breakdown lives in WEAVE_WORK_PLAN.md; detailed requirements and acceptance criteria in WEAVE_DRP.md.

Risks

What we watch, and how we contain it

RiskLikelihood / impactMitigation
Rebrand decays. A forbidden name survives in a filename, a log line or a database identifier and teaches everyone the old vocabulary.high / medThe name-guard grep runs on every commit and fails the build. M0's gate is the first place it must return zero, and it never stops running.
Multi-user writes on file-based stores lose data (drawn above). The JSON store is whole-file read-modify-write.med / highPostgres is the documented multi-user path. M3's gate drives N concurrent writers on every storage path and asserts one winner; the file path is documented as single-operator.
We copy branch code. The Weave layer lives on an unmerged branch, 23 commits ahead, whose review findings were fixed in place.med / highCopy from the pinned commit recorded in PROVENANCE.md, carry the tests with it, and re-run the prior review's findings as regression tests — starting with the workspace-keyed claim lock.
Fork divergence. The parent keeps moving; our copy silently rots.med / medThis is a fork by intent, not a mirror. PROVENANCE.md pins the source commit; picking up a later parent change is a deliberate, reviewed port with its own decision entry — never an automatic sync.
Two production database paths. Postgres and Neo4j both have to work.med / medM1's gate runs the suite green on all three paths. If Neo4j cannot hold that bar it ships labelled experimental rather than quietly half-working.
P0 is enormous. ~92k LOC moving at once is a large blast radius.high / medP0 is mechanical by definition — copy and rename only, zero behaviour change — so its gate is "the same tests still pass at the same count", which a mechanical change can actually meet. Any behavioural fix found in P0 is deferred to a later phase with its own task.
Deferring CRDT co-editing bites. Teams may find 409-and-merge too coarse for prose and diagrams.low / medThe live layer is built behind a transport seam. Revisit if the artifact merge-conflict rate becomes a real complaint — a new decision entry, not a silent redesign.
The wizard becomes a second source of truth — a config the runtime does not actually read.low / highM4's gate is behavioural: a wizard change must be observed as a 403 or 409 on the next request. A wizard that writes anything the runtime does not enforce fails the gate.
Locators rot. A node points at a path that moved, so the index leads nowhere and quietly loses the team's trust.med / highLocators carry a rev, so they resolve against the revision they were written for rather than a moving HEAD. A resolver check runs over every artifact node — M2's gate fails on a single dangling locator, and the same check runs as a periodic job afterwards.
The model migration loses history — lifting reviews and learnings out of task records drops data nobody notices is gone.low / highThe migration is asserted by count and content against the pre-migration records, is idempotent, and leaves the source fields readable until M2 is signed off — then removes them in one commit so the two never coexist.
Onboarding stays a demo. The bundle works on the machine that built it and nowhere else.med / medM6's gate runs on a clean machine with only Docker and the repo, following the published steps verbatim, and asserts a live fleet at the end. Any documented step without a command behind it fails the gate — which is what stops the parent's "call these Python functions" pattern coming across.
In one line

Copy the proven engine out once and rename it wholly ours, then spend the build on what the parent never had — real users, a model that answers the team's questions and leads back to the real document, a live surface, wizards that speak the team's language, a seat for the human who leads the fleet, and one command that stands the whole thing up.
